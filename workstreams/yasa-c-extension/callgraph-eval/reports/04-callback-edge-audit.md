# 回调修复版新增调用边的精确率审计（curl）

对象：回调修复版相对 yasa-fixed 新增的已解析记录 1,199 条（1,195 个“调用行-目标”对，196 个调用行）。这些边不在原评分口径的总体内。

## 第一层：类型可行性（全量，独立于 Yasa）

`extract_field_stores.py` 用 libclang（与 gold 相同的编译数据库，190/190 单元解析成功）独立提取：
- 函数被存入哪个“struct.字段”（赋值，含宏展开出的赋值；初始化列表按 clang 语义形式映射字段）：81 个字段；
- 通过函数指针字段调用的调用点：252 个调用行。

`check_type_level.py` 核对：新增的每条边，目标是否在 clang 认定的该行被调字段的存储集合中。头文件原型按 gold 中唯一的外部定义归一化。

| 结果 | 条数 |
| --- | ---: |
| 目标确实存入该行调用的字段 | **1,199 / 1,199** |
| 不在存储集合中 / 该行无字段调用 | 0 |

反向：clang 的 252 个字段调用行共 1,232 个“行-目标”对，修复版漏 37 对（15 行）：`Curl_cwtype.do_write/do_flush`（sendf.c 3 行）、TLS 多后端 `Curl_ssl_multi` 的 `multissl_*`（vtls.c 11 行）、`version.c` 1 行。

第一层只说明实现与“按类型汇总”的定义一致，**不说明边在运行中可发生**。

## 第二层：调用点可行性（人工抽样）

固定种子 20261107，从 196 个调用行中随机抽 20 行，逐条读源码判定该行的全部 121 个目标（`level2-sample.json`，判定与理由见 `level2-verdicts.json` / `level2_verdicts.py`）。

判定标准：调用方在本构建（OpenSSL、zlib、代理、WebSocket；无 HTTP/2、HTTP/3、多 TLS 后端）中执行时，该调用点的接收者能否持有字段为该目标的对象。调用方本身是否可达不判（与 gold 对直接调用的口径一致）。读代码无法确定的记为“不确定”。

| | 条数 |
| --- | ---: |
| 正确 | 72 |
| 错误 | 40 |
| 不确定 | 9 |
| **精确率**（不确定计错 / 计对） | **59.5% / 66.9%** |
| 按调用行 bootstrap 95% 区间 | 42%–77% / 49%–84% |
| 调用行：全部正确 / 含错误 | 9 / 10（另 1 行只有不确定） |

错误的主要来源（都是按类型汇总无法区分的情形）：
- **客户端写入器按阶段排序**（`writer->next`，content_encoding.c、ftp.c、http_chunks.c）：类型相同的 12 个写入器都被连上，但链中 next 只可能是同阶段或更后阶段的写入器；FTP 行尾转换写入器之后只能是 `cw_out`（12 个中错 11 个）。
- **socket 过滤器是链的叶子**（cf-socket.c:1915 `cf->next->cft->query`）：next 恒为 NULL，9 个目标全错。
- **本构建不会实例化的类型**：capsule 过滤器（仅 HTTP/3 下插入）、`Curl_ssl_multi`（未启用多 TLS 后端）。
- **链中位置**：HTTPS-CONNECT 之下不会再是 HTTPS-CONNECT；HTTP-PROXY 之下不会是它自己；客户端读取器循环只停在 CLIENT 阶段。

## 结论

- 新增边全部类型可行；调用点层面精确率约 60%–67%（样本 20 行，区间宽）。
- 召回增加的同时引入了可观的误报，主要出现在按阶段 / 链位置约束的分发上，这是“按类型汇总”的固有上近似。
- 20 行样本的结果不能外推为全项目回调精确率的精确值。
