# curl/libcurl：Yasa C 与 CodeGraph C 实测

修复版 Yasa 已完成本轮真实项目测试：直接调用优于 CodeGraph，精选回调子集仍落后。原版 Yasa 默认堆首轮 OOM；8GB 重跑持续约 69 分 39 秒仍停留模型构建，随后按用户明确要求停止，准召率无法取得。修复候选的成绩单列，不能归给未修复版本。

## 项目与版本

- 项目：[curl/curl](https://github.com/curl/curl/tree/b052c835a32bb3e1e5622dd46ccfaa128d92b750)，8.23.1-DEV，固定提交 `b052c835a32bb3e1e5622dd46ccfaa128d92b750`。
- 范围为完整配置的 `libcurl_static` 目标：190 个 C 编译单元、154,750 行 C 源码，以及 199 个头文件（含生成配置）。命令行工具、测试、示例和第三方依赖实现不进入调用图真值。
- 实际构建成功；OpenSSL、zlib、23 种协议启用。Clang 成功解析 190/190 编译单元，无解析失败，得到 2,674 个项目函数定义和 6,959 对内部直接调用。
- 原版 Yasa：[用户仓库合并后的 main](https://github.com/JarvisDing-sdu/yasa-engine/commit/e2f89d9c8c9edcf554a3eb82ad9e1adcb51e6c40)，`e2f89d9`，包含官方 `59d2234` 与 C 适配；C parser 源码 `3f2141f`。默认约 4GB 堆的首轮在建模阶段自然 OOM，退出码 -6；8GB 重跑保留原代码。
- 修复版 Yasa：用户随后明确授权并行修复并单列复测。Engine 仍是 `e2f89d9`，仅换成隔离修复的 C parser，8GB 堆。修复屏蔽整组已确定且合法的条件指令并保留坐标、未知分支和宏时间线；源码 SHA256 为 `22671ed9f052fab46db8efb23a48cb8de554fc3434e4e9f0c82946be8bcd3e29`。原 58 项加新增回归共 69 项通过，构建/类型检查及独立审查通过。补丁尚未提交或推送；详细哈希见 fixed-run-manifest.json。
- CodeGraph：[colbymchenry/codegraph v1.6.2](https://github.com/colbymchenry/codegraph/releases/tag/v1.6.2)，源码 `6560052a6f856855d3f71eee838fd66ccfa4285d`，darwin-arm64 发行包；Node v24.16.0。版本按本轮启动时冻结。
- 机器：Apple M5、10 个逻辑 CPU、24 GiB 内存。构建与独立基准已完成后才运行分析器。

## 结果：三种口径必须一起看

- 原版 Yasa（8GB 重跑）：用户主动停止，尚无已验证的完整调用图，准召率无法取得，不记为零。

- CodeGraph v1.6.2：无宏直接调用函数对精确率 **99.27%**，召回率 **98.14%**（TP 5711 / FP 42 / FN 108）。
  调用点级：精确率 99.39%，召回率 98.42%（TP 7391 / FP 45 / FN 119）。
  完整 AST 直接调用对召回率 **83.01%**（5777 / 6959）。
  精选真实回调子集：按唯一源码行归因找到 **9 / 25**（36.00%）。

- 修复版 Yasa（8GB，未提交候选）：无宏直接调用函数对精确率 **100.00%**，召回率 **99.43%**（TP 5786 / FP 0 / FN 33）。
  调用点级：精确率 100.00%，召回率 99.24%（TP 7453 / FP 0 / FN 57）。
  完整 AST 直接调用对召回率 **98.82%**（6877 / 6959）。
  精选真实回调子集：按唯一源码行归因找到 **0 / 25**（0.00%）。

“无宏直接调用”精确率仅适用于可按位置归因的固定直接调用框架，**不是完整输出图精确率**。完整 AST 召回包含宏展开；精选回调子集也不是全项目间接调用召回率。

## 如何避免偏袒某一方

1. 三组接收同一份 C/H 源码与生成配置，389 个源文件的 SHA256 保持不变。两版 Yasa 通过相同 CLI 接收实际构建的宏、头文件路径和 macOS/arm64 编译器宏；CodeGraph 使用正常索引入口。
2. Clang 真值及 11 个回调点均在查看工具输出前生成、校验和冻结。未将真值裁剪成两边都识别出来的函数交集。
3. 固定无宏框架有 8,577 个直接调用坐标，其中 7,510 条内部调用点边、5,819 对内部函数关系；含宏展开或同行混合间接调用的部分另列。它覆盖完整直接调用对的 83.62%。
4. 主指标严格匹配 caller、文件、行、列。另保留“只有一个编译器调用坐标的源码行”回退结果，未用回退替换主指标。
5. 保留文件和函数名，并检查当前构建的定义范围，避免把另一平台的同名实现算正确。跨文件声明映射只允许唯一外部链接函数；静态函数不跨文件补配。
6. 外部函数与未解析占位不当作已解析内部函数，缺失的内部真值仍计漏报。有效间接边不会被错算为直接调用误报。

## CodeGraph 的实际强项与缺口

CodeGraph v1.6.2 使用 tree-sitter，并有结构体回调字段、函数指针注册/传播和宏表的启发式规则；“纯字符串匹配”并不准确。curl 当前配置的 2,674 个函数名称恰好全部唯一，名称解析表现强是合理结果；此项目不能单独证明静态重名/作用域处理谁更强，也不能外推 C++ 或 Rust。

宏缺口是实际调用的缺失，不能只归因于编译器 helper：主框架以外共有 1,140 对关系，其中 1,134 对涉及宏，6 对仅因混合调用行排除。宏相关的 1,134 对里，CodeGraph 在整张图中仅出现 59 对（5.20%）；这属于函数对存在性检查，不保证对应原宏调用点被正确定位。

只有 44 对属于 Wcurl 类型检查 helper，其余缺失包含 `Curl_failf`、`Curl_infof`、`Curl_conncontrol`、状态处理和字符串集合访问等真实目标。例如 `cf-h1-proxy.c:667` 的 `failf`、`ftp.c:3750` 的 `connclose` 和 `cookie.c:1682` 的 `CURL_EASY_STR`。完整清单见证据包的宏审查文件。

修复版在同一宏相关排除集中找到 1,085/1,134 对（95.68%）；其中普通目标为 1,085/1,090 对（99.54%），CodeGraph 对应为 59/1,090。44 对 helper 仍按原规则计漏报，未为了展示分数而从完整 AST 指标删除。

CodeGraph 在严格无宏框架的 45 条调用点误报均指向当前配置未激活的实现。108 对漏报经独立抽查分为：47 对缺少 caller 函数节点、42 对选错 backend、13 对没有对应解析边、5 对挂到错误的 `if` caller、1 对仅在非当前配置调用位置出现。

回调边原始列坐标缺失，故精确坐标分数不能直接解释为没有回调能力。按可唯一定位的源码行计 9/25，若只看 caller-target 是否在图中出现则为 10/25（40%）；多出的 HMAC init 关系来自同一 caller 的另一调用点。

## 覆盖与局限

- 修复版无宏直接调用共漏 33 对/57 个调用点；独立核对同一 caller、同一源码行均无输出记录，属于漏遍历/漏发边，未因修复成绩较好而删掉。完整 AST 缺 82 对，其中 44 对为类型检查 helper、38 对为其他目标，仍全部按冻结规则计漏报。
- 精选 11 个回调位置均有无函数定义的未知占位边，修复版未能解析到 25 条预期目标；并非评分器漏配，也未按占位名称猜补命中。修复边界后直接调用能力更好，回调解析仍需改进。
- 函数节点覆盖只是输出中出现的 active 函数：索引图与调用图对孤立函数的表示可能不同，不能直接称为全部 parser 定义识别率。
- 首轮 Yasa 的 V8 日志明确显示 JavaScript heap out of memory，尚未产图。monotonic 计时约 45 分 51 秒，起止 UTC 跨度约 16 小时 26 分；计时口径及可能的宿主休眠/挂起影响使两者不一致，不能把其中任一项直接当作可控性能比较。8GB 重跑的原始起止和资源参数另保留；它是用户主动停止，区别于首轮自然 OOM。
- 独立 parse-only 检查发现原 C parser 的 ERROR 恢复把 `cf_haproxy_date_out_set`、`curlx_pnow`、`Curl_ossl_ctx_init` 中的 15 个 if 放在文件层。CPU 样本观察到模块层 if 进入深层函数解释，BVT 合并是样本热点。98 行有效 GNU17 反例与指令屏蔽对照支持局部因果关系；修复后全量 census 的这些顶层 if/loop/return 全部消失，带解析诊断的文件由 89 降为 64。修复版模型构建 0.428 秒，整次进程记录 151.477 秒；全部改动在查看修复版分数前已冻结，未为提高已见分数继续改算法。
- 全 AST 的 6,959 对是编译器语法调用关系，包含宏和部分路径不可达分支；不是运行轨迹真值。完整图的精确率没有足够完整的间接调用真值，不能可靠给出单一数值。
- CodeGraph 还有 3,947 条无法对应编译器直接调用行的记录（其中 3,528 条来自未激活 caller），1,263 条位于间接调用行、71 条 caller 未归因、22 条直接调用行坐标不匹配。这些未评估/其他配置记录在证据中保留，不因未进入主框架就被宣称正确。
- 精选回调的 11 点/25 边覆盖 MIME、MD5、HMAC、协议状态机和 FTP 析构五类机制。该子集按可审计目标来源选择，不是随机样本，也不是全部回调。
- CodeGraph 报告索引 390 个文件：389 个 C/H 和被识别成 PHP 的 `lib/Makefile.inc`；后者没有进入 C 调用指标。`lib/multiif.h` 有解析告警。
- 运行耗时仅为现场记录：CodeGraph 进程约 2.80 秒，修复版 Yasa 约 151.48 秒。两者运行时均存在其他分析进程或缓存差异，因此不报告严格速度倍数。原版 Yasa 解析阶段约 46.1 秒；后续阶段见原始日志。用户取消了原先 20 分钟截止，之后在修复版完成后明确停止原版；此次退出并非超时。

## 证据与复核

`Curl-C-callgraph-results.json` 保存原始计数、两种位置归因口径、运行参数及状态。`Curl-C-callgraph-mismatches.json` 保存可追溯的 FP/FN、回调缺失和原始边 ID。

`Curl-C-callgraph-evidence.zip` 保存同源输入、Clang 真值、冻结声明、原始 CodeGraph 数据库、Yasa 原始输出/日志、归一化结果、评分程序、审查记录和构建配方。解压后可对已有 normalized.json 重新评分；实际重跑分析器需安装固定版本及其依赖，并按 run.json 调整本机路径。没有把环境安装或运行成功包装成准召率证据。
