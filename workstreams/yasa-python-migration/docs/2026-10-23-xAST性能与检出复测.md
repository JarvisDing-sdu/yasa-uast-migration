## 输入和复测环境

800 文件从 `alipay/ant-application-security-testing-benchmark` 的 `d825758202b89066f48f4ff87d4d3539b944f513` 检出到临时目录；`sast-python3` 的 Git tree 是 `26d186433dd6fc301cc4ab24f475a817a4968f25`。本地另一个 800 文件 checkout 有 26 个文件的标注行不同，本次没有使用它。旧官方 macOS ARM64 二进制从 [YASA-UAST v0.2.18 发布页](https://github.com/antgroup/YASA-UAST/releases/tag/v0.2.18)获取，SHA-256 `071ec14f24ab82f5cfbf988563dec716918dd2902eb359a39c687edc13d8b538` 与发布资产摘要相符。

新版 UAST 使用历史提交 `c64cb8a`；旧 Visitor 是 v0.2.18。Engine 采用 `9f61576` 的临时快照，因为[原记录列出的 `0e69c5f`](xast-detection-performance.md#测试环境)尚未包含递归目录 runner；两个提交之间仅该 runner 不同，当前工作区的 runner 同样固定扫描 12 文件。依照原记录的命令直接传入 800 文件路径，会实际扫描 12 文件，所以本次在临时快照中使用 `9f61576` 的原有递归 runner。当前工作区源码没有为复测而修改。

本次旧二进制是历史文档的 **v0.2.18**；用户原始 Engine `deps/uast4py/uast4py` 的资产哈希对应官方 **v0.2.19**。两者不能混称为同一二进制基线。

本机为 macOS ARM64、Node.js **24.14.1**、CPython **3.14.8**，原记录为 Node.js 25.9.0、CPython 3.14.5。旧 oracle 的纯 Python 依赖通过 `PYTHONPATH` 指向本机已安装的 Python 3.13 虚拟环境；脚本实际由 Python 3.14.8 执行。历史依赖锁文件与当前安装目录不构成完全相同的运行环境，因此只比较本次新旧两侧在同一机器、同一输入上的结果。

## 800 文件：解析和检出

历史版本的 `tests/corpus.ts` 连续启动三个独立进程，均解析 800/800 个文件，无失败；其“读取＋解析”分别为 **195.6 / 205.7 / 154.4 毫秒**，中位 **195.6 毫秒**，进程 RSS 中位 **114.25 MiB**。当前工作区的新版解析器在相同输入上也为 800/800，无失败；三个进程的“读取＋解析”中位为 **158.0 毫秒**。这两组三轮分开执行，有明显波动，不宜把中位数差直接归因于代码版本。

旧 v0.2.18 Visitor 与历史新版逐文件比较，**800/800 个 UAST `body` 严格相同**，包括位置与元数据。完整 Engine 检出在新旧各三轮中均处理 800 文件、得到 351 条告警；六份告警全文的 SHA-256 完全相同。没有对 800 文件宣称 SARIF 文件原始字节相同；这里复现的是原记录使用的告警全文口径。

| 完整 Engine 指标 | 新版三轮 | 旧 Visitor oracle 三轮 | 中位数与差异 |
| --- | --- | --- | --- |
| Engine 内部总耗时 | 3.400 / 3.262 / 3.111 秒 | 4.861 / 4.809 / 4.819 秒 | 新 3.262、旧 4.819 秒；新版少用 32.3% |
| 命令墙钟 | 3.85 / 3.55 / 3.36 秒 | 5.09 / 5.03 / 5.05 秒 | 新 3.55、旧 5.05 秒；新版少用 29.7% |
| 内部 `parseCode` | 543 / 509 / 499 毫秒 | 2,227 / 2,167 / 2,178 毫秒 | 新 509、旧 2,178 毫秒 |
| Engine Node 进程峰值 RSS | 529.61 / 563.81 / 528.23 MiB | 585.52 / 589.14 / 594.78 MiB | 新 529.61、旧 589.14 MiB；新版少约 59.5 MiB |

峰值 RSS 用每轮独立 Node 子进程的 `resource.getrusage(RUSAGE_CHILDREN).ru_maxrss` 测得；旧侧**不含其调用的 Python 子进程峰值**，与原记录的内存限制相同。它不能代表两个解析器单独的内存占用。原记录绝对值新 264.41、旧 324.78 MB，和本机约 530/589 MiB 明显不同；不应跨环境比较绝对值。

## “快约 92 倍”的计时范围

官方 v0.2.18 二进制按原命令 `--rootDir … --output … -j 1` 连续运行三次，每轮均成功处理 800/800 文件，并各写出 **800 个 JSON、合计 15,532,177 字节**。墙钟分别为 **11.64 / 13.92 / 15.15 秒**，中位 **13.92 秒**；程序自身报告的处理时间中位 **2.36 秒**，`user + sys` CPU 时间中位约 **2.33 秒**，峰值 RSS 中位 **34.55 MiB**。历史新版的 195.6 毫秒是 `corpus.ts` 的读取和解析时间，**不含 Node 启动和 JSON 写出**。旧二进制墙钟与这个数相除得到约 71 倍，仍然是不同工作范围之比。

为了检查旧侧墙钟的来源，同一二进制解析**空目录**两次，实际耗时仍为 **10.18 秒和 19.89 秒**，CPU 仅约 0.26–0.28 秒，也没有写出 JSON。因此，原记录称“墙钟大头在写文件 I/O”不能由本次证据支持；大量时间发生在不处理任何源码时，属于二进制调用或运行环境开销，具体等待点尚未隔离。原记录用旧侧 CPU 时间与新版 136.8 毫秒相除得到的“约 13 倍”，仍把旧侧的序列化和写出混入了解析器比较。

另外做了双方**预加载同样源码、预热 100 文件、只计构建 UAST** 的进程内实验，排除了读取、启动和 JSON 序列化；每侧三个进程、每进程三轮，共九轮。旧 v0.2.18 `ast.parse`＋Visitor 的中位数为 **85.2 毫秒**，历史新版 Tree-sitter＋Visitor 为 **109.3 毫秒**；在这批较小的 xAST 文件上，**旧侧进程内解析反而更快**。这与新版完整 Engine 扫描更快可以同时成立：完整扫描的旧链路还经过 Python 子进程和 UAST 的 JSON 传输、转换与后处理。该进程内结果只适用于此输入和本机，不代替真实项目的其他性能测试。

## 606 文件补充案例

从 `main-forYasaTest@32a74f8dec9dcacfd99a9053ebd8b545a34e09c7` 的 `sast-python3/case` 恢复输入，并按照 `engine/test/python/prepare-python-benchmark.ts` 排除 `cross_file_package_namespace` 子树，得到 **606 个 `.py`**。新旧 Engine 各扫描一次，都分析 606 文件、产生 **332 条告警**；告警全文和新生成的 SARIF 均原始字节相同。原记录的旧 SARIF 文件未保留在当前工作区，本次旧侧用 v0.2.18 Visitor oracle 重新生成。因此已验证重建输入上两条链路一致，无法验证与当年保存的 SARIF 文件逐字相同。
