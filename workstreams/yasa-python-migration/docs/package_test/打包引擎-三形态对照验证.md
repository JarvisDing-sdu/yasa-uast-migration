## 4. 测试与比较口径

### 4.1 解码层（dumpAST / dumpAllAST）

- 单文件：`--dumpAST --single --report <file.json>`
- 批量：`--dumpAllAST --report <dir>`；输出文件名 = `md5(源文件绝对路径)`，因此两侧可逐文件配对
- UAST canonical 规则（与 `verify_old_new_emitter_corpus.py` 口径一致）：
  - 丢弃 `loc`、`sourcefile`
  - 可选丢弃引擎内部派生字段 `_meta.nodehash`
  - `Literal` 的 float / number 值归一化（`1.0` 与 `1`、大整数文本）

### 4.2 检出层（污点追踪）

- checker：`taint_flow_test`；规则：`engine/test/python/rule_config_xast_python3.json`
  （source `taint_src` → sink `FuncCallTaintSink(os.system, args=[0])`）
- 比较脚本：`workstreams/yasa-python-migration/scripts/compare_yasa_sarif.py`
  - `identity` = `ruleId + 文件URI + startLine + startColumn + message.text`
  - `normalizedResultsEqual` = **完整 result（含 codeFlows / threadFlows 的每一跳）**逐字段相等
  - 仅忽略派生字段 `nodeHash`，并归一化旧基线的 `/case/` source-root 拼写

### 4.3 性能

- `/usr/bin/time -v`：墙钟 + 峰值 RSS
- 引擎自带 `scan_summary.json`：分阶段耗时（`parseMs` / `parseCodeMs` / `processModuleMs` / `startAnalyzeMs` / `symbolInterpretMs`）与 `execCount`（解释器指令执行次数）
- 所有扫描统一 `--workerCount 1`，保证可比

分阶段耗时与资源（同一语料、`--workerCount 1`）：

| 阶段 / 指标 | ① 官方（uast4py 外部进程） | ② 源码路径（node22） | ③ 打包（pkg / node18.5） |
| --- | ---: | ---: | ---: |

要点：

1. 解析快了约 **4.9×**（19.3 s → 3.9 s），`parseCode` 快约 **12×**，这是迁移的直接收益；
2. `execCount` 三者完全相同（96,378），说明**执行的指令与语义完全一致**；
3. ② 的分析阶段（5.3 s）与 ① 基本持平，所以**源码路径整体比官方快 2.2×**；
4. ③ 的分析阶段被拖到 **79.0 s（约 16×）**，把解析收益全部吃掉，整体反而比官方慢 **3.2×**；
5. ③ 的构建日志里有成片的 `Warning Failed to make bytecode node18-x64 ...`，与"快照无 V8 code cache、热循环失去优化"的特征一致。

### 5.5 解析失败清单（旧能解析、新不能）

1000 文件批次 3 个、2000 文件批次 4 个，**全部属于同一类语法：tuple 内的星号解包**。

```python
# torch/_higher_order_ops/flex_gemm.py:660
return None, *(
    flex_gemm_autograd_not_implemented(grads[0], like)
    for like in ctx.saved_tensors
)

# torch/_higher_order_ops/associative_scan.py:814
return *[None] * 3, *g_xs, *[None] * num_additional_inputs

# torch/_vendor/quack/rmsnorm.py:1663
return dx, dw, db, dresidual, *([None] * 5)

# torch/distributed/elastic/rendezvous/utils.py:90
host, *rest = endpoint, *[]
```

旧引擎对这 4 个文件全部解析成功（`uast4py` 无 `Failed to parse` 记录），新引擎在 worker 中报
`invalid Python syntax (ERROR)`，并写出 `null` dump。

### 5.6 最大差异类的真实源码形态

```python
raise RuntimeError(
    f"The autograd.Function's vmap staticmethod returned an "
    f"incompatible (output, out_dims) tuple. "
)
```

- 旧 parser（CPython visitor / `uast4py`）：相邻字面量被**合并**为 1 个 `Literal`
- 新 parser（tree-sitter visitor）：保留为 `Literal + Literal` 的 **`BinaryExpression('+')` 链**

`other` 类抽样（`torch/_library/triton.py`、`torch/_dynamo/polyfills/io.py` 等）显示：

- 参数默认值表示：旧为 `NoneType`，新为 `Literal(dict)`（语义相同，编码不同）
- 少数文件表达式列表元素个数差 1（旧 4 / 新 3，同时少 2~3 个 `Identifier` / `BinaryExpression`），需逐个对源码定性

## 6. 已知问题与风险

| 优先级 | 问题 | 证据 | 建议 |
| --- | --- | --- | --- |
| P0 | **pkg 打包后分析阶段慢约 16×**（整体 3.2× 慢于官方） | §5.3；源码路径无此问题 | 换打包策略（Node SEA / nexe / bun compile）或性能验收采用源码路径口径；也可先 `--cpu-prof` 定位解释器热点 |
| P1 | 解析覆盖下降 4/2000（0.2%） | §5.5 | 修 tuple 星号解包语法缺口，并补回归用例 |
| P2 | 大批量 dump 曾出现**静默丢文件**（862/2516，进程仍 exit 0） | 同批测试内的第一次运行；后续 2 次独立运行均为 2430 | 大批量 dump 单独运行、固定 `--workerCount 1`，并在流程中**校验产出数量** |
| P3 | 环境性坑：`/tmp` 会随 WSL 重启清空；后台脚本在会话结束时可能收到 SIGHUP（`exit 129`，不在引擎错误码表内） | 本次实测 | 产物写入持久目录（如 `~/bench`），重要长任务前台运行 |
