# 重新打包验收：1000 PyTorch 与 xAST 污点流（2026-10-20）

## 1. 结论

**本轮验收通过。**

1. 当前代码能够通过真实的 TypeScript 类型检查、`require()` 检查、引擎全量测试和三平台 `pkg` 打包；
2. 新 Linux 打包引擎对固定的 **1000 个 PyTorch Python 文件全部产生有效 UAST**，没有再出现裸 tuple 星号解包失败；
3. 在官方 xAST Python3 完整 **799 文件**靶场上，旧引擎与新打包引擎均产生 **356 findings / 352 个命中文件**；
4. 两份 SARIF 的 SHA-256 完全相同，因此不仅数量一致，**finding 身份、codeFlows 和 threadFlows 的每一跳都一致**；
5. 新引擎的 xAST `symbolInterpret` 为 2.338 s，未再出现先前打包版约 79 s 的 GC 性能退化。

本结论只证明本轮固定语料与规则下的等价性，不把 799 个合成靶场扩大解释为任意 Python 项目的完全等价证明。

## 4. 实验结果

### 4.1 PyTorch `dumpAllAST`

| 指标 | 官方旧打包引擎 | 当前最终打包引擎 |
| --- | ---: | ---: |
| 有效源文件 UAST | **1000 / 1000** | **1000 / 1000** |

| 速度 | 1.00× | **1.51×** |

新包相对旧包墙钟减少 33.6%，峰值 RSS 减少 37.1%。最终包两次生成的 1001 个 JSON 逐字节相同，说明结果稳定。

旧新 parser 的 UAST 不是为“逐字段必须完全一样”设计。本批去掉 `loc` / `sourcefile` 并忽略派生 `nodehash` 后，212 / 1001 个 JSON 完全同树；其余包含已知的 tuple、字符串拼接和类型表示等形状差异。因此真正的语义验收还要看下游分析结果，不能只看 AST 字段数。

## 5. 本轮发现并修正的问题

### 5.1 `npx pkg` 假成功

本机 `engine/node_modules/.bin/pkg` 和 `.bin/tsc` 是异常的 0 字节入口。旧 `build.sh` 运行 `npx pkg` 时以 0 退出，却没有生成任何二进制，属于假成功。

修正后直接调用真实 CLI：

```text
node node_modules/typescript/bin/tsc
node node_modules/pkg/lib-es5/bin.js
```

修正后真实执行了类型检查、编译和 `pkg`，三个产物均存在。

### 5.2 本地 parser 副本可能过期

`@ant-yasa/uast-parser-python` 是 `file:../uast/parser-Python` 依赖，版本号始终是 `0.0.0`。普通 `npm install` 可能复用 `engine/node_modules` 里的旧副本，导致子模块已修复、打包引擎却仍然失败。

`build.sh` 现在会：

1. 检查 `../uast/parser-Python` 是否存在；
2. 显式构建该 parser；
3. 删除引擎中的旧 parser 副本；
4. 重新安装，并通过 SHA-256 确认源构建产物与引擎安装副本一致。

### 5.3 真实大文件中的星号解包回归

先前的兼容逻辑遍历整个源文件，会把报错行之前已经合法的 `f(a, *args)` 也列为替换候选，导致安全校验拒绝重解析。这是小样例通过、PyTorch 大文件仍失败的原因。

最小修正：只在 Tree-sitter 标记的顶层 `ERROR` 子树中寻找待兼容的 `*`，不触碰其他已经合法的 splat。新增“前面有合法 splat，后面有裸 tuple splat”回归测试。Python parser 的 2 个测试文件全部通过，两个先前失败的真实文件也已单独通过。

### 5.4 打包资源不应跨仓库直接引用

`pkg.assets` 原先同时引用 `engine/node_modules` 和 `../uast/parser-Python/node_modules` 中的同一类 WASM。后两条是冗余的跨仓库路径，而且本轮曾在打包后观察到 `uast` 子模块目录消失。

移除跨仓库 assets，只保留引擎安装依赖中的 WASM 后：

- 三平台打包成功；
- Linux 包的 PyTorch 与 xAST 验收通过；
- 构建结束后 `uast` 子模块仍然存在。

### 5.5 Infinite 同学 PDF 中的修复是否已进入当前仓库

PDF `python-uast-migration-summary.pdf` 主要记录了：Python Tree-sitter 迁移、Python/PHP parser 统一初始化、Java benchmark 准备、macOS Rosetta 与 PHP WASM patch。

其中最关键的初始化修复 `5d63b79` 已经包含在当前 `engine@43e2692`；去除强制 GC 的 `1dd836a` 也已包含。因此本轮的打包难点不是 PDF 中的初始化修复未推送，而是后续独立问题：本地 `npx` shim 异常、parser 副本刷新、大文件 splat 回归和跨仓库 assets。

## 7. 仍需注意

1. `npm install --package-lock=false` 每次可能重新解析大量依赖，本轮单次等待数分钟；后续应单独改进为可锁定、可缓存的安装流程；
2. 三个平台包都已生成，但本轮只在 Linux x64 实际运行；macOS 产物需要对应机器验收；
3. PyTorch 旧新 UAST 的其余结构差异应继续使用已有分类报告解释，不能因为 xAST 结果一致就宣称任意下游工具都等价。
