# Yasa C/C++ 真实项目扫描后续计划书

日期：2026-11-08　状态：待确认的方案；本次只写文档，未开始实现。

## 1. 我们接下来要得到什么

对一个同时包含 C、C++ 的项目，运行一次扫描，得到一份能追溯到实际源码的漏洞报告。工具按照项目真实的编译方式理解代码，能沿着 C 与 C++ 之间的调用继续追踪输入，不把未扫描、解析失败或尚未建模的部分当成“没有漏洞”。

这轮优先补齐真实项目扫描的基础：编译配置、头文件上下文、跨语言符号连接、污点流和可信的结果统计。现有 C、C++ parser 继续保留，公共代码继续复用；安装包、目录改名和整体前端替换不列为这轮目标。

用户已经明确的要求：重视真实项目的扫描效果；现有功能不下降；保留基线和原始结果；不做测试特判、不改标签；重要进展用中文报备；推送、合并、发布另行确认。

本文涉及的新模式名称、编译器辅助预处理和工程拆分，是本计划提出的实现选择，尚待用户确认。

## 3. 总体做法

新增显式的 `--language c-cpp` 模式，保留原来的 `c`、`cpp` 命令和报告行为。新模式读取编译命令清单，为每一次真实编译创建独立上下文，选择现有 C 或 C++ parser，再进入同一项目范围内的符号、调用图和污点分析。

第一版聚焦 Linux/macOS 上的普通 C/C++ 编译单元及当前 M1 能处理的普通函数、命名空间、指针和 C ABI 接口。新增能力不通过改变旧模式默认值来开启；旧模式的共享代码重构必须单独提交并通过原回归。

### `.h` 的具体规则

`common.h` 没有固定的“C 身份”或“C++ 身份”。在 `app.c` 的编译过程中包含它，就使用该次 C 编译的语言、宏、包含顺序和搜索路径；在 `main.cpp` 中包含它，就使用该次 C++ 编译的上下文。源文件在 include 之前写的宏，也必须影响头文件。

同一个头文件可以在不同上下文出现多次；只有上下文等价时才能共享解析结果。不能只按文件名缓存，也不能只多加一个 C/C++ 标记就认为足够。缓存需要覆盖编译参数、输入和传递依赖的内容、实际预处理结果及 parser 版本。

头文件中的普通代码告警定位到原头文件，并保留“从哪个编译单元进入”的证据。宏生成的操作以展开调用点为主位置；能获得定义点时另作相关位置。必须准确恢复文件与行号，无法从预处理行标记恢复的列不伪造。`#line` 的逻辑文件/行保留显示，实际输入文件和内容哈希另存作物理证据；不能把逻辑文件名当成真实磁盘依赖。嵌套宏的完整 token 来源不列为本轮承诺。同一漏洞跨多个编译单元重复出现时，可以汇总展示，但不能丢掉配置来源。

### 编译清单与程序边界

优先使用 `compile_commands.json`。它提供单个编译单元的源文件、工作目录和编译命令，同一文件可以有多个编译命令。[Clang 编译数据库规范](https://clang.llvm.org/docs/JSONCompilationDatabase.html)

编译清单本身不等同于完整的链接目标说明。本计划另设“构建选择清单”：选择本轮使用的编译记录，并声明哪些记录属于同一个程序/链接范围。不同可执行程序、测试程序或互斥构建配置保持隔离，最后只汇总展示结果。

初版正式混合扫描要求这两份清单齐全。目标信息可由工程准备阶段从构建系统生成，随后一次命令复用。缺失或无法确认目标归属时，报告说明无法完成混合连接；原单语言模式仍可使用，但不会被标记成完成了正式混合分析。

### 预处理：先验证一个可行的技术路线

新模式拟使用实际 Clang/GCC 驱动的只预处理阶段，保留宏展开、include 顺序、内建宏和源位置标记，再交给现有 tree-sitter 前端。`-E` 的职责是只运行预处理器。[Clang 命令行说明](https://clang.llvm.org/docs/ClangCommandLineReference.html)

这样可以避免把项目的真实条件编译重新猜一遍。这里复用现有 UAST 转换，不等于换成 Clang AST，也不等于获得完整的 C++ 类型语义。

编译器环境也属于配置：记录驱动路径/版本、语言标准和影响 include 的环境；无法复原未记录的历史环境时明确说明。

这条路线先过小型可行性验收：头文件代码确实进入 UAST；源码位置能还原；系统头声明和库模型不会相互破坏；多上下文不会串用；原有两种模式不变。若这几项不成立，阶段停止并重新评审前端方案，不继续把错误结果带入污点分析。

初版支持直接 Clang/GCC 驱动、`arguments` 数组及 POSIX 引号形式的 `command`；保留标准、目标、宏和 include 参数的顺序，只剥离编译/输出/依赖生成动作。响应文件、包装器、预编译头、模块、MSVC/CUDA 等初版不认证；遇到时明确报不支持，不能静默丢参数后声称按原配置扫描。不会执行构建脚本、源程序或原始 shell 命令。

## 4. 推进顺序与每阶段交付

### 阶段 A：收口现有版本，冻结对照

独立复审 M1 修复；复现和修正单文件 `.h` 的显式语言选择；保存两种旧模式的配置、输入版本、结果哈希和原始证据。后续新能力在隔离分支中开发，分支名由执行时确定，不修改现有基线文件。

交付：M1 复审结论、`.h` 回归用例、可复现的基线清单。未通过时不进入大范围集成。

### 阶段 B：按真实编译上下文看对代码

读取编译数据库和构建选择清单；完成编译器辅助预处理、源码位置映射和按编译单元解析。覆盖共享 `.h`、不同宏、include 前的宏、生成头文件、同文件不同配置、主线程与 worker 一致性。

系统头声明保留用于识别调用，系统实现按库模型处理；项目自己的函数体正常分析。不得把“跳过整个系统头”当成正确建模；无法保留必需声明时记录覆盖缺口。

交付：每个编译单元的配置及依赖清单、预处理产物、UAST、位置映射、诊断；小型真实可构建项目上的技术可行性报告。此时只承诺前端上下文正确，不承诺跨语言漏洞已打通。

### 阶段 C：连通跨语言调用和污点

以构建范围为边界建立统一符号索引：C 接口与 C++ `extern "C"` 正确匹配；C++ 普通同名函数不误接到 C 函数；在同一编译单元中，后续定义也要继承先前匹配的 extern C 声明，不能只看定义外面有没有 wrapper（[语言链接规范](https://eel.is/c++draft/dcl.link)）；`static`、匿名命名空间、头文件内部定义按编译单元隔离。相同源码位置但不同配置的函数实例不能互相覆盖。

头文件中的定义按链接属性处理。普通 C++ 外部 inline 函数在同一个程序内是同一实体；来源、签名和预处理体等价时共用函数及其局部 static 存储。static inline 和匿名命名空间定义仍按 TU 隔离；命名空间级 const 等默认内部链接也按真实 C++ 规则识别，不照搬 C 的规则。外部 inline 体冲突记录为冲突，不以先出现者覆盖。这一共享规则见 [C++ inline 规范](https://eel.is/c++draft/dcl.inline)，内部链接规则见 [C++ linkage 规范](https://eel.is/c++draft/basic.link)。为此增加跨两个 TU 设置/读取局部 static 的危险及安全对照；只要求本轮已支持的普通值/指针、同一符号执行路径内共享，不扩展到完整动态初始化顺序。

同一个分析实例跟踪 C 与 C++ 函数之间的参数、返回值及指针写回。规则保持原有 source/sink 语义，统一输出一份 SARIF 和带上下文来源的调用图。重载、方法等超出 M1 的调用记录为未建模，不能按裸名强行连边。

交付：双向跨语言危险链与安全对照通过、函数指针接口测试、错误连边负例、重复告警与配置归属说明。声明“混合扫描支持”必须等这一阶段完成。

### 阶段 D：用真实项目检验效果

先跑冻结的受控混合用例，再跑已有真实项目。优先候选：

- `aria2` 本地版本 `9e7273583f83e881e3ec067b523ba88724088d2f`：存在 C++ `.cc` 主体和 wslay C 源码；核对实际启用 wslay 的构建目标后，作为首个混合候选。
- `cppcheck` 本地版本 `8df3087f48aa70a2e0e54ec05324f7147ec3e0b6`：作为复杂 C++ 解析与覆盖诊断候选。仓库里的 C 测试样例不自动算作其可执行程序的 C 组成部分。
- curl：沿用既有冻结输入和调用图 gold，继续作为 C 不退步的对照。

当前只核对了仓库内容和版本，未生成这些候选的有效构建配置、未运行新模式。aria2 未发现构建编译数据库；cppcheck 现有同名 JSON 是 GUI 手工测试夹具，不可当作该项目的真实构建数据库。下一阶段需在独立构建目录中生成并验证，依赖安装、下载或构建按已有工作约定先报备。

交付：可复现构建配置、逐项目覆盖报告、调用图核验、告警人工审计与已知漏洞样本结果。不因某项目效果不好而从清单中消失；构建失败、未支持语义和性能失败都保留记录。

### 阶段 E：按漏报原因安排 C++ M2/M3

完成混合基础后，再分别写类/成员/虚函数、引用别名、动态全局初始化、STL/字符串与文件流模型的实施计划，保持每项可独立验收。此次计划不会把这些能力提前算作完成。

## 5. 怎样判定“扫得准”

不用一个笼统的“正确率”包住全部情况，分别记录：

- **误报**：在有标签的用例中算 TP/FP；真实项目将告警逐条标为成立、误报、证据不足。证据不足单列，不算已确认正确。
- **漏报**：固定 gold/已知漏洞中的 FN；真实项目不知道所有漏洞时，不宣称掌握整个项目的召回率。
- **覆盖**：计划扫描的编译单元、成功/部分/失败的单元、未解析片段、未建模构造、无法解析的调用、超时及排除项。读过文件不代表已经分析完。
- **复现与代价**：源码/编译配置/规则/工具版本、原始报告和日志、耗时与峰值内存。

评分先按 gold 中明确列出的上下文实例匹配：case、profile、domain、根 TU 和 sink/调用点实例都需对应；头文件相同位置在不同上下文可以有不同标签。先评分、后展示去重，一次命中不能抵掉另一个上下文的漏报。

冻结实例因构建、预处理、解析或超时无法完成时，整组验收失败、不发布正式通过分数；另列失败正例/负例和完整原分母。若展示部分统计，同时给出“已检出危险实例 / 全部冻结危险实例”，不能缩小分母。运行完成但因未建模而漏掉的 gold 正例仍计 FN。证据不足的真实告警保留未知类别，同时给出保守确认比例 TP/全部已审告警，不能只算已确认的子集。

受控混合用例必须能真实编译和链接：先冻结源码、构建配置、危险/安全标签及预期调用边，再运行工具。覆盖 C→C++、C++→C、`extern "C"`、命名空间外定义、回调、指针写回、共享头文件及宏配置。所有冻结且属于声明支持范围的危险链必须检出，安全对照不得误报；失败就不能宣布该阶段通过。

在真实构建目标中枚举跨语言接口：不超过 30 个调用点时全部核验；超过时至少按固定种子 20261108 抽取 30 个，并覆盖正反方向和可用的回调。Clang AST/编译器信息用于核对声明和直接调用，间接调用另做人工 gold；参考工具的输出不自动等于完整真值。

已知漏洞清单在新模式运行前冻结，优先选可构建且根因明确的修复前/后版本。找不到合适样本、样本漏报或编译失败，就如实记录，不能用注入缺陷冒充真实漏洞。真实项目没有完备 gold 时，只报告审计范围内的结果。

## 6. 不退步的硬门槛

每个实现任务先写失败测试、确认失败再修复。涉及 Engine 或 parser-C 的任务必须跑完整 C 回归；涉及 C++ 路径同时重跑 CPP 测试。保留旧标签、旧原始结果和基线文件，增加的结果另存。

C 对照：原 72/112 项测试全部通过；sast-c TP110/FN0/TN54/FP0 且逐例相同；2,451 个 UAST 哈希相同；四组 Juliet C 逐例相同；curl 严格调用点 TP7453/FP0/FN57、full_ast 6877、人工回调 25/25，三个评分对象完全相同。

CPP 对照：原 parser-CPP 18、Engine CPP 40 项全部保留；计分器 13 项与自测通过；原 M1 修复版的 8 份 Juliet CPP 完整 JSON 不退步。若以后语义模型使某些 FN 变 TP，单独解释和审计，不覆盖冻结对照来消除差异。

新模式的正式验收还要求：所有计划单元都有终态；无隐藏跳过；无 worker 配置串用；相同配置可复现；受控源码位置正确；运行失败不伪装成零告警；不把互斥配置或不同程序连接在一起。旧的 C/CPP 扫描模式不会因为缺少新模式要求的编译数据库而停止工作。

## 7. 风险与处理

头文件的依赖多、重复预处理可能增加时间和内存。先验证小目标；仅在依赖和编译上下文等价时缓存。内存、超时有明确预算并在报告中记录，不默认放宽参数来让验收通过。

编译器辅助预处理会暴露更多系统头、模板和扩展语法。发现 parser 或库模型缺口时，保留可恢复结果并标记覆盖不完整；阻碍关键漏洞链时，该目标的效果验收不通过。

多目标和多配置是误连边的主要风险，使用显式构建选择及链接范围隔离。丢失目标信息时不强行构造全项目统一图。

若需要替换整个前端、增加完整 Clang AST、支持 Windows 工具链或 C++20 模块，另起方案；不借本轮混合支持顺带重写现有 C 功能。
